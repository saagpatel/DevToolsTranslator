# ADR-012: Offline Egress And Model Boundary

Status: accepted for Gate 0 review
Owner: privacy/security gatekeeper

## Decision

Core investigation and import workflows are offline-only. The core app and hostile import worker use App Sandbox without network client/server entitlements. They contain no general HTTP client dependency or socket-opening adapter. Source-specific networking lives in separately signed, least-privilege broker processes with a narrow framed IPC contract; each broker has a distinct capability, allowed protocol/address, data contract, disable switch, and audit receipt.

The Native Messaging host is part of a separately distributed Browser Adapter and communicates only over Chrome stdin/stdout. It has no loopback, XPC, local-socket, or core-live-IPC path. The exact-extension manifest, visible inspected-tab DevTools panel, one-use challenge, short-lived credential, monotonic frames, strict metadata payload, explicit stop, private atomic inbox, and offline bundle re-import are separately gated; disconnect or malformed input publishes zero bytes. The host and native adapter are hardened and entitlement-free, and the unchanged core remains exactly two executables. The loopback OTLP broker can bind only `127.0.0.1`/`::1`, requires a per-session attachment credential, enforces non-configurable absolute frame/event/byte/rate ceilings in addition to narrower session quotas, and has no outbound network entitlement. An unauthenticated or malformed peer is rejected without terminating the legitimate source's attachment window. The exact `stop` control frame records a terminal revocation gap; EOF is not treated as user consent to stop. Fragmented frames retain parser state until completion or watchdog expiry. The live receiver tolerates unknown fields only at known OTLP trace-schema locations; hostile file import remains strict. Each accepted frame is projected without raw span names, attributes, credentials, or unknown content. Any rejected frame poisons the session projection. Only a complete projection that passes the evidence kernel may be serialized to an explicitly inherited descriptor; invalid input publishes zero bundle bytes, and the completion receipt binds the byte count and SHA-256 digest. The resulting bundle re-enters through the same native import/kernel boundary. The separately signed OTLP adapter contains a SwiftUI controller with only App Sandbox, network-server, and user-selected-file entitlements plus an entitlement-free Rust helper. Its signed workflow and local lifecycle oracle cover visible consent, endpoint disclosure, inherited-descriptor publication, install, update, downgrade rejection, credential revocation, uninstall, user-export preservation, and absence from the unchanged two-executable core bundle. Fresh-VM notarized lifecycle and real-source operation remain unproven.

Passive local-network context is a second separately signed and distributed native adapter. Its SwiftUI controller is App-Sandboxed with only user-selected-file access; its entitlement-free Rust helper inherits that sandbox, and neither executable has network client/server or privileged entitlements. The visible one-shot workflow discloses the exact fixed `/usr/sbin/arp -an` command and noncausal limits, refuses to overwrite an existing export, supports cancellation, and sends its ephemeral consent capability only through an inherited descriptor—not arguments, environment, request JSON, output, or evidence. The helper cannot publish active-scan commands. Product evidence removes addresses, link-layer identifiers, and interfaces; retains only neighbor state, conflict, count, and explicit limitations; kernel-validates before inherited-descriptor publication; and publishes zero bytes on malformed input. The digest-bound bundle re-enters through the signed core Rust bridge. Signed App Sandbox runtime and local lifecycle checks pass without adding an executable to or mutating the two-executable core bundle. This remains unknown-trust logical context, never topology, ownership, attribution, or causal evidence. Fresh-VM, notarization/stapling, and manual accessibility/disclosure proof remain unproven.

Selected-application process context is a third separately signed and distributed native adapter. A signed negative control proves that the App-Sandboxed core cannot obtain another process's resource usage; therefore the core does not expose a process command, embed the process helper, request a process-inspection entitlement, or weaken its sandbox. The separate ordinary-permission adapter contains a native SwiftUI controller and Rust helper, both hardened and entitlement-free, with no network client/server APIs. The controller transiently lists visible GUI applications and requires explicit selection. It passes PID and its claimed bundle identifier only in the bounded local request; the helper uses PID transiently, detects PID reuse by executable UUID and process start time, and never serializes PID, path, arguments, user, environment, files, disk, or network activity. Retained fields are limited to the controller-claimed bundle identifier, cumulative user/system CPU time, resident/physical-footprint memory, wakeups, and terminal coverage. The claim is source-declared and explicitly unauthenticated by the helper. Consent and evidence publication use inherited descriptors, EOF is cancellation, invalid input publishes zero bytes, and the kernel-validated bundle re-enters through ordinary offline core import. No relation or causal/process/network attribution is created. Fresh-VM, notarization/stapling, and manual accessibility/disclosure/identity proof remain unproven.

No updater is included or required through Gates 1-6. A future updater must be a separately signed, independently disableable evidence-blind process, disabled by default or enabled through an explicit visible policy. Its requests contain no evidence-derived fields or stable investigation identifiers; failure never blocks local operation.

No evidence field, URL, hostname, process identity, trace, packet, log, model prompt, or derived claim enters analytics, telemetry, crash reporting, updater traffic, or a remote model.

A future remote-model feature requires a new product decision, compile-time feature boundary, per-operation consent, exact field preview, redaction, provider/retention disclosure, and a fresh derived bundle. Output remains `model_generated` and `inferred`.

## Oracle

Artifact checks verify the core/import-worker entitlement and dependency denylist. A negative test injects a deliberate socket/fetch attempt and proves the sandbox blocks it. An OS/proxy/network-syscall monitor additionally proves fixture, import, browse, compare, and export workflows make zero outbound connections. Broker loopback/local-network paths are separately counted and disclosed. Any unexpected connection fails closed and blocks release.

## Rollback

Disable or remove the offending component. No core workflow may depend on an updater, telemetry client, crash uploader, or model endpoint.
